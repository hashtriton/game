# Следующие шаги

Этот список сохраняет цель текущего этапа: подготовить существующий `game`, объединить контекст и доказать работу Unity/Blender через Codex. Он не утверждает дизайн MVP. Начинайте с фактического состояния в [setup.md](setup.md).

## 1. Завершить техническую подготовку и проверки

1. Подтвердить, что используется `C:\Users\Netes\Desktop\proj\game`, прочитаны применимые инструкции, сохранены существующие файлы и локальный Git инициализирован только при его отсутствии.
2. Записать установленные версии Unity Editor, Unity CLI/Pipeline, Blender и Codex. Без вывода секретов проверить действующий Unity аккаунт/лицензию. При необходимости входа дать владельцу минимальный следующий шаг.
3. Проверить актуальные официальные инструкции Unity CLI/Pipeline/MCP и BlenderLab MCP. Установить только необходимые официальные компоненты в пределах разрешений. Новые соглашения, credentials и изменения security остановить до подтверждения владельца.
4. Настроить локальный MCP с минимальной областью доступа. До включения Blender Python без sandbox оценить изоляцию и необходимые разрешения; не открывать публичный порт.
5. Выполнить реальную нейтральную операцию из Codex. Для Unity подтвердить открытие пустого 3D проекта и компиляцию. Для Blender создать простую сцену/примитив, сохранить `.blend` и экспортировать в проверенный поддерживаемый формат. Не добавлять чужие материалы.
6. Проверить клиент-сервер, транспорт и результаты операции. Если конфигурация действует только после перезапуска/следующей сессии, записать это отдельно от результата текущего исполнителя.
7. Сохранить безопасные логи и результаты в `setup.md`: подтверждено, не проверено, заблокировано. Проверить комплект документов и Git; не добавлять Unity-кеши, временные файлы и секреты.

Если шаг заблокирован, фиксируйте точное действие, программу/URL, риск и нужное подтверждение. Независимые документы, резервные копии и подготовку минимального проекта продолжайте.

## 2. Сделать исследование воспроизводимым

- 5 октября по отдельному поручению получены локальные карты 3.4/3.9c и Dota snapshot, выполнен разбор и записаны source/hash/commit. Начать с [базы механик и баланса](lia-mechanics-balance.md) и [индекса данных](../research/lia/README.md).
- Перед проектированием конкретной механики прочитать [ревью](lia-review.md) и [правила применения](lia-data-use.md), запустить обычный `lia_validate.py` с проверкой snapshot. Это исследовательская база; неоднозначные profiles, defaults и динамические эффекты проверять отдельно.
- Держать исследовательские материалы отдельно от собственного кода и игровых ассетов; отметить права и запреты на повторное использование.
- При необходимости углубить анализ конкретной механики воспроизвести её на зафиксированной версии. Для Dota проверять реально вызываемый код, а не только KV. Для Warcraft 3.4 не выдавать оптимизированный JASS за полный GUI-исходник.
- Текущая обычная загрузка Warcraft 3.9c прошла с HTTP 200; прежний 403 не обходился. Данные 3.9c получены отдельно и существенно отличаются от 3.4. Перед выбором baseline проверить оставшиеся динамические ветки и поведение в соответствующем движке.
- При обновлении аудитории сохранять периоды, пропуски и определения метрик. Не суммировать записи лобби и дневные пики в «число игроков».

## 3. Согласовать небольшой игровой прототип

После подтверждения инструментов сформулировать вместе с пользователем собственную ценность игры и один проверяемый игровой цикл. Сначала решить режим первой версии, цель проверки и границы MVP; затем выбрать минимальное число героя/противников/предметов, длительность и камеру для этой проверки. Исследовательские числа LiA использовать как материал для сравнения, не как автоматически принятые параметры.

Прототип должен проверять конкретную гипотезу, которую можно наблюдать: например, понятность управления и удовольствие от боя/развития. Конкретная гипотеза, метрики и критерии продолжения пока не согласованы.

## 4. Обсудить проверку спроса и рынок

Steam/Windows рекомендованы для первого рынка, itch.io обсуждался как более ранняя проверка спроса. Ни один вариант пока не утверждён. При будущем решении о Steam заново проверить актуальные условия и взносы перед оплатой; текущий этап не разрешает покупку или публикацию.

Показатели кастомных игр не дают прогноза продаж самостоятельной игры. Нужны отдельные данные о реакции на собственный проект, целевой аудитории и готовности платить. Отсутствие бюджета на платное продвижение учитывайте при обсуждении каналов, не подменяя им бюджет разработки.
